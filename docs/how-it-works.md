# How it works

## Boot chain

1. **DHCP** – the client gets an address plus *next-server* (this host) and the
   boot file `eve-x86_64.efi` (or `eve-arm64.efi`).
2. **TFTP: iPXE** – the firmware loads the iPXE binary. Its embedded script
   ([docker/embed.ipxe](../docker/embed.ipxe)) is generic: it runs DHCP again
   and chains `tftp://<next-server>/boot.ipxe`.
3. **TFTP: boot.ipxe** – written by the `sync` service from `.env`; it chains
   `http://SERVER_IP:HTTP_PORT/eve/eve.ipxe`. Keeping site settings out of
   the binary means the image can be built once and used everywhere.
4. **HTTP: eve.ipxe** – the menu, generated by `sync` whenever releases,
   imports or settings change. Choosing an entry shows a summary; **i** boots:
   - `kernel` with the EVE installer command line + your options
   - `ucode.img` (x86 microcode, when present) and `initrd.img`
   - `installer.iso`, added to the initrd as the cpio entry `/installer.iso`
5. **EVE installer** – the initrd loop-mounts `/installer.iso`, starts
   `rootfs_installer.img` and installs EVE-OS to the target disk.

Leaving the menu with *Boot from local disk* (or the timeout) exits iPXE with a
failure code, so the firmware continues with the next boot device.

## Why not `sanboot` the ISO?

EVE's installer looks for its installation medium again after Linux has
started. An ISO that iPXE emulates as a SAN/CD drive is gone at that point.
EVE's own network boot therefore puts the ISO inside the initrd and boots with
`root=/installer.iso`. EVE-Netboot-Installer does exactly the same, but from
iPXE instead of EVE's GRUB.

The kernel command line is rebuilt per release from the ISO's own
`EFI/BOOT/grub.cfg` and `grub_include.cfg` (memory/CPU settings, flavour
tweaks, `boot/cmdline` …), so changes in new EVE releases are picked up
automatically. It is stored in `meta.json` next to each release.

Consequence: the target needs enough RAM for the kernel plus the whole ISO
(~0.5–0.7 GB) – in practice ≥ 2 GB, ≥ 8 GB for the `k` variant.

## GitHub mirroring

Every `ENI_SYNC_INTERVAL` seconds `sync` lists the releases of
`ENI_GITHUB_REPO`, keeps non-prerelease tags ending in `-lts`, groups them by
`major.minor` and takes the highest patch of the newest `ENI_LTS_LINES` lines.
For each wanted `<arch>.<flavour>.generic.installer.iso` it

- downloads the ISO (up to 3 attempts, each from the start; written to a
  temporary file and renamed when complete),
- verifies it against the release's `*.sha256sums`,
- extracts `kernel`, `initrd.img`, `ucode.img`, `cmdline` and the GRUB files,
- removes releases that are no longer wanted.

The menu shows when GitHub was last checked successfully (stored in
`www/eve/sync-state.json`). Generated files are only rewritten when their
content changes.

## Local imports

`IMPORT_DIR` is scanned every `ENI_IMPORT_INTERVAL` seconds. ISO files with
volume id `EVEISO` and `*installer-net.tar` files are copied to
`www/eve/local/<name>/` and prepared like a release. Files that are still
being written are skipped until their size is stable.

## Data layout (`DATA_DIR`)

```
www/                      served over HTTP
  index.html              status page
  eve/eve.ipxe            the menu
  eve/status.json         machine readable status
  eve/releases/<tag>/<arch>.<variant>/   installer.iso, kernel, initrd.img, …, meta.json
  eve/local/<name>/                      same for imported ISOs
tftp/                     served over TFTP
  eve-x86_64.efi, eve-arm64.efi, boot.ipxe (+ optional aliases)
```

## Services

All three use the same image; the compose `command` selects the role.

| Service | Network | Does |
|---|---|---|
| `sync` | bridge | mirror, import, writes `eve.ipxe`, `boot.ipxe`, status page |
| `tftp` | host | publishes the iPXE binaries, runs `in.tftpd` (tftp-hpa) |
| `web`  | bridge, `HTTP_PORT:80` | nginx, serves `www/` |
